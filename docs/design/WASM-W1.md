# WASM W1: WebAssembly on wasmi

Row WASM. JetStream 2.2's exit metric needs a score. Its five wasm tests (HashSet, tsf,
quicksort, gcc-loops, richards) need `WebAssembly`, which RustKit deliberately does not define
today (`web_interfaces.js`: `typeof WebAssembly` is `"undefined"`, so a page takes its non-wasm
path). Once #1440 lands, the wasm group may be where the run stops. wasmi is approved (Pete,
2026-11-14). It comes from crates.io, **pinned `=2.0.0`** (the version whose source this design was checked
against; 2.0.1 and 2.0.2 exist and are a separate bump; it is in legion5's cargo registry, not the
Mac's, and in no seat's vendored tree) with
`default-features = false` plus only the features W1 uses (`std`, `validate`). Its
`THIRD_PARTY_NOTICES.md` entry is regenerated by `scripts/third_party_notices.py`, not
hand-edited. The licences (MIT/Apache-2.0) don't conflict with the AGPL.

## What JetStream actually calls

These are from the pinned checkout (`JetStream2.2` @ `332d8ee1`), `JetStreamDriver.js` and
`wasm/*.js`. All five are older Emscripten builds with the same glue:

- **The binary.** The driver fetches it with XHR (`responseType = 'arraybuffer'`) and sets
  `Module.wasmBinary`, so the glue takes `WebAssembly.instantiate(binary, info)`. It never takes
  `instantiateStreaming`, which is guarded by `!Module["wasmBinary"]`.
- **Memory.** `new WebAssembly.Memory({initial: N, maximum: N})` with **initial equal to
  maximum**: 52–134 MB fixed (TOTAL_MEMORY 52,428,800 to 134,217,728). The growth paths exist
  in the glue, but they can't succeed against that maximum.
- **Table.** `new WebAssembly.Table({initial, maximum, element: "anyfunc"})`, imported as
  `env.table`.
- **Imports**, read from the five `.wasm` import sections:
  - **every module imports its memory (`env.memory`) and its table (`env.table`)**, both created
    in JS. None defines or exports a memory of its own (so the W1 limit on module-defined
    memories below doesn't touch JetStream);
  - **immutable number globals:** `env.tableBase`, `env.DYNAMICTOP_PTR`, `env.STACKTOP`, and in
    four of them `env.STACK_MAX`, and in two `global.NaN` and `global.Infinity`. These are plain
    JS Numbers given as imports, converted to an immutable i32 or f64 global;
  - **functions:** 7–27 `env.*` JS functions (abort, the stack and heap helpers, time,
    `_emscripten_asm_const_*`, `_pthread_once`).
- **Re-entry.** Wasm calls JS, and that JS calls wasm again inside the same outer call. richards'
  `_emscripten_asm_const_i` import runs `runRichards`, which calls `Module._setup` and
  `Module._scheduleIter`: its whole timed loop runs one level in. HashSet and gcc-loops reach
  `Module.dynCall_v` through `_pthread_once`.
- **Exports.** Functions called from JS (`_main`, `stackAlloc`, ...). The glue makes typed
  views over `wasmMemory.buffer` (`HEAP8` ... `HEAPF64`) and reads and writes them between calls.
- **Score.** The driver's `WasmBenchmark` takes `reportCompileTime` and `reportRunTime`.

So W1 is what those five need, done to the spec where they touch it, with the rest stated.

## W1 surface

On `globalThis.WebAssembly`, in every realm (frames included):

| API | W1 |
|---|---|
| `validate(bytes)` | yes |
| `compile(bytes)` | yes. A promise, settled in a microtask; the work is done synchronously (stated) |
| `instantiate(bytes, imports)` | yes, giving `{module, instance}` |
| `instantiate(module, imports)` | yes, giving an `Instance` |
| `Module(bytes)` | yes, with `Module.exports(m)`, `Module.imports(m)` and `Module.customSections(m, name)` |
| `Instance(module, imports)` | yes, with `.exports` a frozen null-prototype object |
| `Memory({initial, maximum, shared?})` | yes: `buffer.byteLength` is `initial` × 64 KiB, as in Chrome (`{initial:1, maximum:2}` gives 65,536). No grow past `initial` in W1 (below). `shared` is a TypeError (no threads) |
| `Table({element, initial, maximum})` | `anyfunc`/`funcref` and `externref`, with `get`/`set`/`grow`/`length` |
| `Global({value, mutable}, v)` | i32, i64 (BigInt), f32, f64, externref, funcref, with `.value` and `valueOf()` |
| `CompileError`, `LinkError`, `RuntimeError` | yes, as `Error` subclasses |
| `compileStreaming`, `instantiateStreaming` | yes, over a `Response` (`arrayBuffer()` then the above) |

Not in W1 (stated: each is rejected at validation, as Chrome rejects a feature it doesn't support):

- threads and shared memory;
- exceptions (`Tag`/`Exception`);
- the JS Promise Integration API;
- **memory64.** It is in wasmi 2.0's default features, so W1 turns it off in the engine `Config`
  (`wasm_memory64(false)`); Chrome 148 ships it, so this is a stated gap, revisited after W1;
- **SIMD.** It is behind wasmi's non-default `simd` cargo feature, and W1 builds without it. None
  of JetStream 2.2's five wasm tests uses SIMD (checked by validating them with SIMD off, in phase
  5). It is a later row if a page needs it.

## Architecture

- **A new crate, `rustkit-wasm`,** wrapping wasmi: module compile, validate, instantiate, and
  the type mapping. `rustkit-js` stays free of wasmi.
- **`rustkit-bindings` installs `WebAssembly`** with host functions on the realm's host object,
  as the other web APIs do (`web_wasm.js` for the JS half, which holds the classes, promises and
  argument checks).
- **One wasmi `Store` per JS realm,** owned by the bindings. Modules, instances, memories, tables
  and globals are store handles, held by the JS objects that wrap them. A realm's store goes with
  its realm.

### The value boundary (JS API §ToWebAssemblyValue / ToJSValue)

| wasm type | JS to wasm | wasm to JS |
|---|---|---|
| i32 | ToInt32 | Number |
| i64 | ToBigInt64 | BigInt (Chrome) |
| f32 | ToNumber, then f32 | Number |
| f64 | ToNumber | Number |
| funcref | null, or an exported wasm function (else TypeError) | that function |
| externref | any value | the same value |

An exported function is a JS function object (`name` = the function index as a string, `length`
= its arity) whose call runs the wasmi function.

### Calls both ways (re-entry) — a W1 requirement

A JS import is a wasmi host function. A wasm export called from JS runs inside a Boa native call
holding `&mut Context`. When wasm calls a JS import, that host function needs the same context.
JetStream then calls *back into wasm* from that JS (above), while the outer wasmi call still holds
the store mutably. So:

- **Outermost call.** An export called with no wasm frame below it borrows the realm's `Store`
  (one `RefCell` borrow) and calls the function.
- **Inside a host function.** wasmi hands the host function a `Caller` (a live
  `StoreContextMut`). The host-function trampoline pushes a pointer to that `Caller`, plus the Boa
  context pointer, on a per-realm *call stack* before it runs the JS import, and pops both when
  the import returns, by unwind or by exception. The pointers are valid exactly while that host
  function's frame is live.
- **Nested export call.** An export called while that stack is non-empty calls the function
  **through the top `Caller`** (`Func::call` takes any `AsContextMut`). It never re-borrows the
  `Store` from its owner: that would be a `RefCell` double-borrow panic, or aliased `&mut`
  through a raw pointer. Each level saves and restores the same way.
- **Depth bound.** Mixed JS↔wasm nesting is bounded (a constant, set against Boa's own recursion
  limit). Past it, the call throws a `RangeError`, as Chrome's stack overflow does: measured on
  Chrome 148 and pinned (message pattern and catchability).
- **Errors.** An exception thrown by a JS import propagates as that exception through the wasm
  frames, as in Chrome. A trap becomes a `WebAssembly.RuntimeError`. Under `call_resumable`
  (below), a host function's error comes back as `Ok(ResumableCall::HostTrap)`, not `Err`: the
  wrapper drops that invocation and rethrows the JS exception. It never resumes it.
- **Red test:** a JS import that calls back into another export, three levels deep (JS → wasm →
  JS → wasm → JS → wasm), with values checked at each level, plus the depth-bound `RangeError`.

### Memory: one copy, owned by the ArrayBuffer (memories created in JS)

A `WebAssembly.Memory` created in JS allocates **`initial`** pages as an `ArrayBuffer` that script
cannot detach. That's Boa's existing `from_byte_block_with_detach_key`
patch (PATCHES.md "arraybuffer-detach-key"). wasmi runs over the same bytes with
`Memory::new_static`, so there's no copy and no sync at call boundaries. The `ArrayBuffer`'s
storage must never move while the store lives.

- **The `&'static mut` invariant**, stated where the code makes it: `new_static` wants
  `&'static mut [u8]`. The slice really lives as long as the `ArrayBuffer`'s storage. The store
  owns a handle that keeps that `ArrayBuffer` alive, the detach key stops script from taking the
  storage, and nothing in the engine detaches it while the store lives. The store is dropped with
  the realm's bindings (Rust ownership, not a GC root), so the lifetime is the store's. A
  navigation-release test pins that no realm is kept alive by it (#1440's lesson).
- **Resident cost** is `initial` pages per memory from the start: 52–134 MB for each JetStream
  test. wasmi's `new_static` zero-fills the slice, and `AlignedVec` has no zeroed constructor, so
  there's no lazy zeroing.

- **byteLength** is `initial × 64 KiB`, as in Chrome, whatever the maximum.
- **No grow in W1.** `memory.grow(n)` with `n > 0` throws `RangeError` from JS and returns −1 to
  wasm. That's legal: a grow may fail. It's a stated limit, and JetStream's memories have
  `initial == maximum`. `grow(0)` answers the current size. W2 is a Boa patch for an `ArrayBuffer`
  viewing external bytes, so a grow can detach the old buffer and hand out a new one at the new
  size, as the spec says.
- **Module-defined memories** (a module with its own memory section) are made by wasmi's
  `Memory::new` at instantiation; there's no hook to supply the bytes. So in W1 such a memory's
  exported `Memory.buffer` **cannot alias its bytes**. Reading `.buffer` throws a `TypeError`
  naming the limit, rather than returning a copy that writes wouldn't reach. The module itself
  runs. None of JetStream's five has one (above). The W2 external-bytes patch lifts this too.
- **Cap.** A per-realm total of linear memory (1 GiB in W1, a constant), enforced with wasmi's
  `ResourceLimiter`. Past it, `Memory` throws `RangeError`, as Chrome does when its own reservation
  fails.

### The script deadline

A long wasm loop has to honour the live turn's deadline and Stop, the same as JS. wasmi fuel
metering is on (`Config::consume_fuel`). The export wrapper calls with `call_resumable` and a
slice of fuel. When the slice runs out, the call is suspended, not trapped: the wrapper checks the
deadline and the interrupt word (rustkit-js's), then resumes with a new slice, or ends the call
with the same uncatchable stop a JS script gets. A nested call through a `Caller` shares the
outer call's fuel, and **a nested call is resumable too**. In wasmi 2.0.0 a plain `Func::call`
turns `OutOfFuel` into a trap it can't resume (`execute_func` → `into_non_resumable`). richards'
whole timed loop runs one level in (inside `_emscripten_asm_const_i`), so a nested call made with
`call` would trap at the first empty slice instead of checking the deadline. So every export call,
outermost or nested, is `call_resumable`. A nested one goes through the top `Caller` (each
`execute_func_resumable` takes its own stack from the engine's pool, so that works from inside a
host function). On `ResumableCallOutOfFuel`, the wrapper checks the deadline and the interrupt
word, refills (`Store::set_fuel` at the outermost level, `Caller::set_fuel` nested), and resumes.
Red test: an export that loops longer than one slice, called from inside a JS import, completes
under the deadline. A second one is stopped at the budget. The slice size is set by measurement,
as low as overhead allows.

## Tests (red first)

- **API shape and edges, against Chrome for Testing 148** (receipt in `docs/diagnostics/`):
  `typeof WebAssembly`, the constructors' `length`/`name`, `new WebAssembly.Memory({initial:1})`
  `.buffer.byteLength`, `validate` on good and bad bytes, `Instance.exports`' prototype and
  frozenness, an i64 export returning a BigInt, a JS import's exception passing through, a trap's
  error class and message pattern, a `Table` of `anyfunc`, a `Global`'s `value` and mutability.
- **Spec testsuite basics** (WebAssembly/testsuite, hand-picked modules as inline bytes:
  `i32`/`f64` arithmetic, `call_indirect` through a table, memory load/store at the boundary,
  traps), checked against Chrome's answers.
- **JetStream's own first calls:** quicksort's glue with its `.wasm`, run in the engine with
  frames on, to `reportRunTime`. Then the other four. The JetStream score comes from the batch's
  JetStream run.
- **Deadline tests:** an infinite wasm loop is stopped at the budget, and the page lives on. A
  nested export (called from inside a JS import) that runs past one fuel slice completes, and a
  nested infinite loop is stopped at the budget.
- **Module-defined memory:** a module with its own memory section instantiates and runs, and its
  exported `Memory`'s `.buffer` throws the TypeError naming the W1 limit.
- **Number → immutable global imports:** `env.STACKTOP` (i32) and `global.NaN` (f64) given as
  plain JS Numbers are read back by the module, and a non-Number for an i32 global is a
  `LinkError` as in Chrome.
- **A navigation-release test:** an instantiated module's realm is released after navigation.
  This is #1440's lesson about GC roots in host closures, applied from the start.

## Phases (each red, then green)

1. **`rustkit-wasm` with `validate`/`Module`/`Instance`**, numeric exports and imports, and the
   error classes. No memory or table yet.
2. **Memory** (the `new_static` design), the cap, and `buffer` identity.
3. **Table and Global**, `call_indirect`, and funcref across the boundary.
4. **The promise forms and streaming,** and the deadline via fuel.
5. **JetStream's five wasm tests run in the engine;** their compile and run times are reported.

## Costs and risks, stated

- **Speed.** wasmi is an interpreter, so JetStream's wasm scores will be far below Chrome's JIT.
  W1 is about running and scoring at all. Speed is a later row: wasmi's register machine is among
  the fastest interpreters, and a JIT is out of scope.
- **Size.** wasmi and its dependencies add to the binary (measured and stated in the PR).
- **Security.** wasm is sandboxed by construction (wasmi is memory-safe Rust). The new surface is
  the boundary code: re-entrancy through a raw context pointer, scoped to one call, and memory
  over an undetachable buffer. Both get adversarial tests (a host function outliving its call, a
  detach attempt).
